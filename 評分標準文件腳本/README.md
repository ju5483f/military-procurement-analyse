# 評分標準 docx 產生腳本

產生 `控制點篩選結果為所有軍購案評分的標準.docx`（專案根目錄）。

## ⚠️ docx 產出後即為主檔，本腳本不是

使用者會直接在 Word 裡編輯那份 docx。**一旦編輯過，重跑本腳本會覆蓋掉那些修改。**

所以：

- **要小幅修文字 → 直接改 docx**，不要動腳本
- **要改評分機制**（錨點變動、維度合併方式改變、控制點增修）→ 改腳本、重新產生，然後**把使用者對 docx 的既有修改重新併回來**（先用 git diff 看看動過什麼）

## 執行

```bash
node gen_scoring_docx.js      # 需 npm i -g docx
```

## 體例（沿用使用者原檔，不要擅改）

- A4（11906×16838 dxa）、四邊邊界 720 dxa、內文 12pt
- 標題用 `***…***` 包起來——那是使用者自己的標記法，不是 Markdown
- 2 張 5 欄表格：編號｜分析項目名稱｜風險意涵｜風險類別｜評分標準
- 表頭粗體、手動框線、無表格樣式
- 欄寬 900/2200/1300/900/5156（原檔為 1159/2693/2057/2138/2409，總寬相同；因評分標準欄的文字大幅變長而重新分配）

## 已發生過一次的實例：使用者的 Word 修改要回填

1150717 使用者在 Word 補上了作維類的「風險類別」欄（原檔留空，補成與軍投對稱：2-1~2-5、2-10 執行風險，2-6~2-9 財務風險）。該修改**已回填進本腳本**，重跑不會再消失。

這就是上面那段警告的實際情形。往後若使用者又改了 docx，處理方式相同：

```bash
# 1. 先看使用者改了什麼（把 git 版與現行版的文字抽出來比對）
#    參考 1150717 的作法：解開兩個 docx 的 word/document.xml，逐段落／逐儲存格 diff
# 2. 把修改回填進本腳本
# 3. 產生到暫存位置、與使用者的 docx 逐格比對，確認一致後才覆蓋
```

**不要先重跑腳本再處理**——那會直接蓋掉使用者的修改，且 docx 是二進位，git diff 看不出內容。

## 內容的來源

錨點與三項結構決議來自 1150717 的真實資料校準，詳見 CLAUDE.md「風險評分」節。**改動前務必先讀那一節**——成對合併、數值錨點法、軍投 1-10 併入 1-3/1-4 這三件事都是推導出來的，不是偏好。

## 驗證

產生後解開 docx 讀回 `word/document.xml`，確認：

- 無殘留「待定」「本期」「進行排序」「0.00~100.00」
- 有「0.00~70.00」「建立評分標準時」「100億美元」「2億美元」「300％」
- 2 張表各 11 列（含表頭）
- 20 個編號齊全

（1150717 產生時，這些檢查全數通過。）
